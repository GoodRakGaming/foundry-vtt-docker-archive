**Критичный баг найден и исправлен (2026-08-24):** после `systemctl restart foundry-helper` обе панели теряли связь с сокетами насовсем — Docker bind-mount ОТДЕЛЬНОГО ФАЙЛА сокета следит за inode, а хелпер при каждом старте делает `unlink`+`listen` (новый inode); примонтированный в контейнере файл оставался привязан к старому, уже несуществующему inode. Исправлено: сокеты теперь живут каждый в своей директории (`/run/foundry-helper-dm/dm.sock`, `/run/foundry-helper-admin/admin.sock`), в контейнеры монтируется директория целиком, а не файл — так контейнер всегда видит актуальный файл по пути. Перепроверено: рестарт хелпера больше не рвёт панели.

Дополнительно сверх исходного списка: добавлены read-only операции `list-instances`/`get-state` на оба сокета (панели не монтируют registry.sqlite вообще — только через хелпер, см. заметки). Найден и исправлен баг с таймаутом `docker compose up` (60с → 10 мин для операций с возможным pull образа).

**Живой тест хелпера (2026-08-24):** deploy (архив с валидным main.js) → контейнер поднялся, health вернул alive:true → Guard C заблокировал delete активной версии → после сброса active_version delete прошёл, контейнер удалён. ## Заметка: обнаружен блокирующий баг в TheWitcherTRPG v14.0.0 (2026-08-25)

данных: файлы мира скопированы 1-в-1, LevelDB прочитана и смигрирована Foundry без ошибок на сервере.
Поиск по GitHub-issues репозитория `witchertrpg-foundryvtt/TheWitcherTRPG` — совпадений нет,
похоже, баг ещё не задокументирован разработчиками системы.

**Активная версия немедленно возвращена на v13** (v14 в моменте отдавалась реальным игрокам —
краш происходит для 100% актёров, играть невозможно). v13 не тронута, работает нормально.
**Не решено** — нужно либо ждать патча системы, либо самостоятельно репортить баг мейнтейнерам
(https://github.com/witchertrpg-foundryvtt/TheWitcherTRPG/issues), либо копать в сторону того,

## Фаза 11: Настоящая полная миграция + прогресс-бар (2026-08-25)

По решению пользователя: отказ от точечного переноса как основного пути, сделана
**настоящая полная миграция тома** v13 → v14 (все 7 миров, все системы, все 91 модуль разом).
Стало практично именно благодаря Фазе 8/9 (общий склад ассетов) — без выноса сырых
ассетов том v13 весил бы 17+GB, теперь всего 6.6G, полное копирование осмысленно.

**Добавлена async job-модель в хелпер** (по прямому запросу пользователя — "нужен прогресс бар
копирования в панели"):
- `lib/jobs.js` — in-memory реестр фоновых задач (не переживает рестарт хелпера — это ОК, сама
  команда всё равно падает при рестарте процесса, восстанавливать нечего).
- `lib/exec.js`: `runWithProgress()` — spawn + парсинг `NN%` из сырых чанков stdout (rsync
  шлёт прогресс через `\r`, не `\n`, обычный readline по строкам не сработал бы).
- `copy-volume-job` (новая DM-операция): те же Guard B/rate-limit проверки синхронно, сама
  передача — в фоне через `rsync -a --info=progress2`; при ошибке подчищает dst обратно в пустое
  состояние, чтобы Guard B не заблокировал повторную попытку намертво.
- `job-status` (read-only, для опроса).
- ДМ-панель: `/api/upgrade` разбит на `/api/upgrade/start` (бэкап+стоп+старт job) →
  браузер опрашивает `/api/job/:id` раз в 1.5с, живой прогресс-бар → `/api/upgrade/finish`
  (старт назначения). Протестировано на синтетических данных (Guard B, error-cleanup) и живьём.

**Найден и исправлен баг прогресс-бара**: `--info=progress2` без `--no-inc-recursive` даёт
не-монотонный процент — по мере того как rsync докапывается до новых поддиректорий во время
инкрементального сканирования, знаменатель "всего файлов" растёт, и процент может ПАДАТЬ
(живой пример: 95% → 63% посреди реальной миграции). Добавлен `--no-inc-recursive`
(после того как текущая миграция уже успешно завершилась — правка не прерывала живой процесс).

**Живой прогон:** бэкап v13 (6.6G) ~15 минут → остановка v13 → rsync-копия ~10 минут (быстрее
tar, без сжатия) → фикс порта в options.json v14 (снова 30013→30014, та же грабля что при
первом деплое) → старт v14 → возврат v13 в строй. `reconcile` чист, все 7 миров в v14, оба
контейнера живы. **Активная версия сейчас v14** — пользователь сам переключал туда-обратно
несколько раз параллельно с миграцией (видно в audit_log), последний раз оставил v14 — не менял
это решение.

**Место на диске критично: 8.4GB свободно из 116GB (93%)**. Найден и удалён битый бэкап-огрызок
(1GB, обрубленный тем самым таймаут-багом из Фазы 10) — не восстанавливается, безопасно снесён.
Крупнейший резерв на будущее — `/opt/foundryvtt`+`/opt/foundrydata` (~17.5GB, оригинал systemd-
установки), но по политике проекта трогать его рано (правило "минимум месяц после боевой сессии

## Фаза 16: Исправление Guard B + перевод всех сообщений (2026-08-25)

**Настоящая причина бага "data/v14 is not empty".** Guard B (запрет полной миграции в непустое
назначение) проверял `readdirSync(dataPath).length === 0` — то есть буквально "есть ли что-то на
верхнем уровне data/<version>". Но:
1. Мой же фикс в Фазе 13 (создание `Data/` заранее с правильными правами, чтобы избежать EACCES)
   гарантирует, что `Data/` существует сразу после деплоя.
2. Docker сам создаёт точки монтирования shared-assets (`Data/art`, `Data/tokens` и т.д.) при первом
   старте контейнера.
3. Foundry сам кладёт `README.txt` в `Data/worlds`, `Data/systems`, `Data/modules` и создаёт
   `options.json` при первом запуске.

Итог: любая когда-либо запущенная версия навсегда считалась "не пустой", хотя реальных данных
(миров/систем/модулей) там не было — это ломало ровно тот сценарий, для которого система и
задумывалась: (a) развернуть новую версию → (b) сделать в неё полную миграцию → почистить лишнее
через сам Foundry.

**Исправление:** новый `lib/guardB.js` с функцией `isEmptyForGuardB()` — считает "непустой" только
если внутри `Data/worlds`, `Data/systems` или `Data/modules` есть хотя бы одна **папка** (реальный
мир/система/модуль всегда папка, README.txt и другие файлы игнорируются). Используется одинаково в
`checkVolumeEmpty.js` (пре-проверка в панели), `copyVolumeJob.js` и `copyVolume.js` (сама
проверка перед копированием) — раньше эта логика была продублирована в трёх местах с риском
разъехаться, теперь один источник истины.

**Проверено:** `check-volume-empty` для v14 (реально содержит README.txt в worlds/systems, 1 файл в
modules, плюс служебные Data/<shared-category> заглушки) теперь возвращает `empty:true` — сценарий
(a)+(b) разблокирован.

**Перевод сообщений на русский.** Прошёлся по всем `OpError`/`Error` в `helper/operations/*.js`,
`helper/lib/*.js` (validate, zipslip, ratelimit, compose) и роутам `panel-admin/index.js` —
переведены все, что реально долетают до панелей (не тронуты только протокольные ошибки уровня
сокета типа "invalid JSON", которые обычный пользователь через браузер никогда не увидит).
`panel-dm/index.js` уже был на русском.

**Уточнение схемы работы (замысел пользователя, зафиксировано для памяти):**
- (a) Деплой новой версии Foundry через админ-панель.
- (b) Полная миграция тома из старой версии в новую (теперь действительно работает на свежем
  деплое) — дальше лишнее удаляется, нужное обновляется через сам Foundry Setup.
- (в) Точечный сценарий ДМ: просто копирует мир (+ систему, если её нет — уже так и работает),
  модули устанавливает сам через Foundry Setup при необходимости. Изменений не потребовалось —
  copy-world уже соответствует этому описанию.

## Фаза 17: Остановка теста, очистка бэкапов панели, живой ресканинг + проверка места (2026-08-25)

**Остановлена тестовая полная миграция.** В момент запроса шёл `tar -czf` бэкапа v13 (шаг
backup-volume внутри /api/upgrade/start) — v13 к этому моменту ещё не была остановлена, поэтому

**Исправлена проблема "Foundry не видит скопированные данные без перезапуска".** Foundry сканирует
`Data/worlds`, `Data/systems`, `Data/modules` один раз при старте процесса, не следит за
файловой системой. `dst` в полной миграции (и вообще любой задеплоенный инстанс) работает
непрерывно с момента деплоя — вызов `start` с `--no-recreate` для уже запущенного контейнера ничего
не делает, поэтому `/api/upgrade/finish` не приводил к реальному пересканированию.

Добавлена новая операция хелпера `restart` (`docker compose restart`, безусловно перезапускает
контейнер независимо от текущего состояния, с health-wait по аналогии с `start`). Подключена:
- `/api/upgrade/finish` (обе панели используют один и тот же helper) — теперь реально перезапускает
  `dst` вместо бесполезного `start`.
- `/api/copy-world` и `/api/copy-modules` (обе панели) — после успешного копирования (что-то
  реально скопировалось) проверяют, жив ли `dst` сейчас, и если да — перезапускают его тоже.
  Если `dst` был остановлен, ничего не трогаем — при следующем обычном старте Foundry и так всё
  увидит. Результат (`restarted`/`restartError`) отображается в сообщении панели.

**Проверка свободного места добавлена везде, где раньше её не было.** Аудит показал: только
`backup-volume` проверял место (`MIN_FREE_BYTES_FOR_BACKUP` = 2 GiB). `copy-volume`/
`copy-volume-job` (полная миграция), `copy-world`, `copy-system`, `copy-modules`, `deploy` — не
проверяли вообще. Добавлен общий `lib/diskspace.js` (`freeBytes`, `usedBytes`, `requireFreeSpace`).
Полная миграция и `copy-modules` считают реальный размер данных, которые будут скопированы

порог `MIN_FREE_BYTES_SAFETY` = 2 GiB (переименован из `MIN_FREE_BYTES_FOR_BACKUP`, теперь общий).

**Проверено:** `restart` через сокет реально перезапустил v14 (health alive после), периметр
DM/admin не пострадал (`copy-volume-job` по-прежнему отклоняется на dm-сокете). `freeBytes`/
`usedBytes` дают корректные цифры на реальных путях (20.9 GiB свободно, v13 занимает 6.5 GiB) —
после очистки бэкапов у полной миграции v13→v14 достаточно места, гейт не будет ложно блокировать.

## Фаза 19: Встроенный апдейтер Foundry разрешён насовсем (2026-08-25)

**Проблема:** обновление v14 (Build 361 → Stable 367) через сам Foundry (Setup → Обновление
программы) падало с "You do not have permission to write files...". Причина — по архитектуре
`/opt/foundry/apps/<version>` монтируется в контейнер как `:ro` (сознательно, чтобы файлы версии
менялись только через контролируемый `deploy` в админ-панели), плюс папка физически принадлежала
root, а Foundry внутри контейнера работает под uid 1000.

**Решение (осознанный выбор пользователя, НЕ временная лазейка):** пользователю явно предложены два
варианта — (1) обновлять только через админ-панель как новую версию + встроенные инструменты
переноса, (2) разрешить встроенный апдейтер навсегда. Выбран вариант 2: "встроенный апдейтер должен
всегда работать, никакой временной лазейки".

Изменения:
- `lib/compose.js`: `addService()` и `refreshServiceMounts()` теперь монтируют `/app` как `rw`
  вместо `ro` — применяется ко всем будущим `deploy`.
- `operations/deploy.js`: добавлен `chown -R CONTAINER_UID:CONTAINER_GID appPath` после распаковки
  архива (раньше `chown` делался только для `dataPath`) — иначе `rw`-монтирование ничего не даёт,
  Foundry всё равно не сможет писать в файлы, принадлежащие root.
- Существующие v13/v14: перегенерированы через `compose.refreshServiceMounts()` (та же функция,
  что использует сам код, не ручной sed), `apps/v13` и `apps/v14` перевладены на uid 1000. v14
  пересоздана (`docker compose up -d`), чтобы новый mount-режим применился — проверено изнутри
  контейнера (`touch /app/write-test.tmp` прошёл). v13 сейчас не запущена, подхватит на следующем
  старте без доп. действий.

**Осознанный компромисс, зафиксирован явно:** теперь файлы версии могут меняться в обход
контролируемого `deploy` (встроенным апдейтером Foundry) — инвариант "версия неизменна, меняется
только через deploy" больше не гарантирован. Реестр (`node_image`) при этом не обновляется
автоматически, так что если апдейтер когда-нибудь потянет версию с другим требованием к Node
(маловероятно в пределах патчей одного major, но теоретически возможно при смене канала обновлений
на "Тестирование"/"Разработка"), это не будет отражено в реестре — риск принят пользователем.
